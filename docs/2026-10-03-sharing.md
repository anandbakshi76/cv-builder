# Sharing (Phase 4)

## What exists now (no server needed)
| Way to share | How it works | Privacy |
|---|---|---|
| **PDF / Word / text** | Export As → pick a format and send the file yourself. | The file contains exactly what you chose in Print options (photo, personal details). |
| **E-mail** | Export As → Send Email opens a draft in your own email app (a `mailto:` link) with your CV text; you attach the PDF yourself. | Nothing passes through this app; your email app sends it. |
| **QR code** | Export As → QR Code encodes a **contact card** (name, headline, email, phone, profile links) or one profile link, as a PNG you can download or print. It is generated in your browser and decoded back in testing to confirm it scans. | The contact card never includes date of birth, address or nationality. Anything you encode is readable by whoever scans it. |

### QR code use cases
Job fairs (print it on the back of a CV or a name badge), networking events and business cards (a LinkedIn or portfolio QR), a poster or slide at a careers event. A contact-card QR lets the scanner save you as a contact in one tap; a profile-link QR opens your LinkedIn or GitHub directly.

## Share link (public, read-only): not built yet, decision needed
The request was: click "Get Share Link", get `https://yourdomain.com/share/abc123xyz`, anyone with the link can view, download the PDF and print, with options to copy it, show a QR and **revoke** it.

That needs somewhere to keep the CV so that other people's browsers can read it, i.e. **a backend**. The app is deliberately browser-only (Phase 1: no server, nothing leaves the device) and may be hosted statically (GitHub Pages), where a backend cannot run. Adding one changes the privacy model (CVs, with names, phone numbers and possibly photos, would be stored on a server), adds running costs and security work, and was therefore held back for an explicit decision. Options:

1. **Hosted share service (matches the request).** Server-side storage keyed by a random ID, a read-only `/share/<id>` page, and a secret delete token for revocation.
   - Needs a host that can run server code and a store (Vercel + a database/KV, or any Node host + a database). Not possible on GitHub Pages.
   - Needs: random unguessable IDs (at least 128 bits), a size limit, rate limiting, no public listing, a delete token kept in the owner's browser, an expiry policy, a privacy notice, and a decision about the photo (store it or leave it out).
   - Short, scannable QR codes for the share URL work here.
2. **Serverless link (no storage).** The CV is compressed and placed in the part of the URL after `#`, which browsers never send to any server. Works on any static host, nothing is stored anywhere, and nothing can leak from a server. Limits: the link is long (hundreds to thousands of characters, too long for a clean QR), the photo would have to be left out, and a link cannot be revoked (anyone who already has it keeps the data); "revoke" would only mean "stop handing it out".
3. **Do nothing for now** and keep using file, e-mail and QR sharing.

Recommendation: option 2 if the project stays static and private; option 1 only if you are happy to host and look after personal data. Tell me which one (and, for option 1, where it will be hosted) and I will build it, including the "Get Share Link" menu entry, copy-to-clipboard confirmation, the share page, and a QR code that points at the share URL.

## E-mail details
- `mailto:` format: `mailto:<to>?subject=My%20CV%20-%20<Name>&body=<CV text>`; the address is optional and validated.
- Body is cut at about 1,800 characters (longer links are truncated by several mail clients); "Copy full CV text" copies everything.
- A backend e-mail service (sending the PDF as an attachment from a server) was not built: it would need server credentials, a server to hold them, and a decision on abuse protection, and it falls under the same hosting question as share links.

## Privacy and revocation, summarised
Today nothing is uploaded, so there is nothing to revoke: delete the downloaded files or QR PNGs yourself. If a share service is built, revocation (deleting the stored copy through the secret token) and an expiry date must be part of it from the start.
